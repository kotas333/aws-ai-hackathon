## E1. ヘルスケア・環境データ連携

### US-1.1【M】★ ヘルスケアデータの自動取得

**As a** 疲弊した社会人ユーザー  
**I want** アプリを開いたときに、ヘルスケアアプリの行動履歴(歩数、運動時間、心拍数等)が自動的に読み込まれる  
**So that** 動けないソファの上でも、追加入力なしに自分の状況をAIに伝えられる

#### Acceptance Criteria

- **Given** ユーザーが初回起動時にヘルスケアアクセスを許可している  
  **When** ユーザーがアプリを開く  
  **Then** 当日0時から現在までの歩数・アクティブエネルギー・運動時間・心拍数・睡眠時間・立ち上がり時間の6項目が自動取得される

- **Given** ヘルスケアデータの取得に失敗した(権限拒否、API障害等)  
  **When** 取得処理が走る  
  **Then** 「データ取得に失敗しました」のメッセージが表示され、ヘルスケアデータなしでも対話生成に進める(フォールバック)

- **Given** 当日のヘルスケアデータがゼロ(まだ何もしていない朝など)  
  **When** 取得処理が走る  
  **Then** ゼロ値として正常に処理され、天使悪魔の対話生成に渡される

#### 備考
- 取得項目はIntent定義v4で確定済み(計6項目)
- ヘルスケア生データは**端末ローカルにのみ保持**し、AWSには送信しない(NFR / リスクR3対応)

---

### US-1.2【M】 ヘルスケアアクセス許可フロー

**As a** 初回起動のユーザー  
**I want** ヘルスケアアプリへのアクセス許可を、なぜ必要かの説明と共にリクエストされる  
**So that** 安心してデータ提供できる

#### Acceptance Criteria

- **Given** 初回起動である  
  **When** ヘルスケア許可ダイアログを出す前  
  **Then** 事前説明画面で「天使がデータを参照して話す」ことが説明される

- **Given** ユーザーが許可をすべて拒否した  
  **When** アプリが起動する  
  **Then** 「ヘルスケアなしでも遊べます(精度は落ちます)」と案内され、利用継続できる

---

### US-1.3【M】★ 位置情報と天気データの取得

**As a** ユーザー  
**I want** 自分のいる地域の天気・気温が自動的に取得される  
**So that** 「真夏の猛暑日」「梅雨どき」など環境を踏まえた天使の意見を聞ける

#### Acceptance Criteria

- **Given** ユーザーが位置情報利用を許可している  
  **When** 対話生成リクエストの直前  
  **Then** 現在地の気温(℃)、天気(晴れ/曇り/雨/雪等)、湿度が天気APIから取得される

- **Given** 位置情報が拒否されている、または天気API取得失敗  
  **When** 対話生成リクエストの直前  
  **Then** 環境データなしで対話生成に進める(フォールバック)

#### 備考
- 位置情報は**取得時のみ使用し永続保存しない**(プライバシー配慮 / リスクR3対応)
- 天気APIは無料枠のあるサービスを選定(OpenWeatherMap等)

---

### US-1.4【S】 取得データのプレビュー表示

**As a** 透明性を求めるユーザー  
**I want** 天使悪魔が議論する前に、取得されたデータの要約を確認できる  
**So that** 「何を根拠に話されているか」を理解できる

#### Acceptance Criteria

- 取得データのサマリー(歩数◯歩、気温◯℃ 等)が、対話表示の上部または別画面で確認できる
- データに納得いかない場合、対話生成前に「やり直し」ができる

---

### US-1.5【M】★ 迷惑リスク判定(新規 / v4対応)

**As a** プロダクト  
**I want** 取得したヘルスケアデータと環境データから「周囲への迷惑リスク」を判定し、フラグとして対話生成に渡す  
**So that** 悪魔がリスク高時に柔らかく入浴を推奨する仕様(US-2.4)を実現できる

#### Acceptance Criteria

- **Given** ヘルスケアデータと環境データが取得できている  
  **When** 対話生成リクエストの直前  
  **Then** 以下のプロキシ指標から複合条件で**迷惑リスクフラグ**を計算する:
  - 最終入浴からの経過時間(72時間超でリスク高方向)
  - 運動量(歩数・運動時間・アクティブエネルギーの合算スコア)
  - 気温・天気(夏場・湿度高時は閾値短縮)
  - 心拍数(発汗量の推定)

- **Given** 計算結果  
  **When** プロンプト構築  
  **Then** リスクレベル(low / medium / high)と各指標の値がプロンプトに含まれる

- **Given** データが部分的に欠損している  
  **When** 計算処理  
  **Then** 取得できた指標のみで暫定スコアを算出し、欠損ありフラグを付ける

#### 備考
- 閾値の具体値はConstruction Phaseで詳細化
- LLMが最終判断するハイブリッド方式(Intent v4の健康配慮ポリシー)
- このストーリーは**Healthcare Integration Unit**ではなく独立した**Risk Assessment Unit**として扱う可能性あり(Unit分解時に判断)

## E2. 天使と悪魔の対話

### US-2.1【M】★ 天使と悪魔の対話メッセージ生成(v4更新)

**As a** ソファで動けないユーザー  
**I want** 天使と悪魔がデータを根拠に対話してくれる  
**So that** 自分で判断する代わりに、二人の議論を眺めて気持ちを整理できる

#### Acceptance Criteria

- **Given** ヘルスケアデータ・環境データ・迷惑リスクフラグが揃っている  
  **When** 対話生成リクエストが送られる  
  **Then** Amazon Bedrockに対し、データ・キャラクター設定・原則・リスクフラグを含むプロンプトが送信され、天使と悪魔の対話形式メッセージが返ってくる

- **Given** Bedrockからの応答  
  **When** 画面に表示する  
  **Then** 天使と悪魔のメッセージがそれぞれ識別可能な形(アイコン、色、左右配置等)で交互に表示される

- **Given** Bedrockからの応答  
  **When** 表示完了  
  **Then** **悪魔の発言が必ず最後に来る**(設計原則の厳守)

- **Given** Bedrockからの応答  
  **When** 表示  
  **Then** どちらのキャラもユーザーを真剣に責める表現は含まない(プロンプト設計で担保)

- **Given** **基本トーン**  
  **When** 通常時の対話  
  **Then** 悪魔は積極的にダラけ・サボりを推奨する(v4の「振り切り」方向)

- **Given** ネットワークエラー、Bedrock障害  
  **When** リクエスト失敗  
  **Then** 「ちょっと考え事してます…」等のフォールバック表示と再試行ボタンを出す

#### 備考
- プロンプト設計はDomain Modelの中心(Construction Phaseで詳細詰め)
- リスクR4・R7・R14対応:プロンプトのテストを早期に実施
- 応答時間はNFRで「数秒以内」目標、超過時はローディング表示

---

### US-2.2【M】 対話のターン数

**As a** 短時間で済ませたいユーザー  
**I want** 対話が長すぎず短すぎないターン数で完結する  
**So that** 2〜3分の利用時間に収まる

#### Acceptance Criteria

- 対話のターン数は**4〜6ターン**(天使→悪魔→天使→悪魔→…)を目安とする
- 全ターンを生成・表示するのに5秒以内を目標とする
- ストリーミング表示(キャラごとに順次表示)も可とする

---

### US-2.3【S】 キャラクターの口調を選べる

**As a** 自分好みの体験をしたいユーザー  
**I want** 天使悪魔の口調・人格をいくつかのプリセットから選べる  
**So that** 飽きずに使い続けられる

#### Acceptance Criteria

- 天使と悪魔のペアとして、**最低2セット**のプリセットを用意(例:標準セット、関西弁セット)
- 設定画面でペアを切り替え可能
- 切り替え後は次回の対話生成からプロンプトに反映される

#### 備考
- MVPでは「標準セット」のみで動かしてもよい

---

### US-2.4【M】★ 悪魔の発言トーンシフト(新規 / v4対応)

**As a** 過度なサボりで健康を損ないかけているユーザー  
**I want** 連続サボりが長期化した時や、迷惑リスクが高まった時に、悪魔のトーンが柔らかく健康寄りにシフトする  
**So that** 自分のサボりパターンに気づき、必要に応じて入浴できる

#### Acceptance Criteria

- **Given** 連続サボり長期化を**綺麗度の悪化度合い**で検知(データ駆動)  
  **When** 対話生成リクエスト  
  **Then** プロンプトに「連続サボり長期化フラグ」が付与され、悪魔の発言が穏やかな健康寄りトーンになる(例:「最近お風呂入ってないっぽいけど大丈夫?」)

- **Given** 迷惑リスクフラグが`high`(US-1.5)  
  **When** 対話生成リクエスト  
  **Then** プロンプトにリスクフラグが付与され、悪魔も柔らかく入浴を推奨する(例:「さすがに今日は入っといた方がいいよ、明日仕事でしょ?」)

- **Given** トーンシフト発動時でも  
  **When** 対話生成  
  **Then** 悪魔は「天使のような厳しい説教」はしない。**あくまで柔らかい・甘やかし口調を保ちながら、内容として健康寄りにシフト**する

- **Given** ユーザーが結果として「サボる」を選んだ  
  **When** 選択完了  
  **Then** トーンシフト発動時でも、悪魔は最終的にユーザーの選択を肯定する

#### 備考
- このストーリーはIntent v4の健康配慮ポリシーの中核
- リスクR14対応:プロンプト設計が複雑になるため、Boltで段階的に導入
- トーンシフトの発動条件・閾値はConstruction Phaseで詳細化

## E3. 選択と履歴

### US-3.1【M】 入る/サボるの選択

**As a** 議論を聞き終えたユーザー  
**I want** 「入る」「サボる」のボタンをタップして選択する  
**So that** 自分の意思を記録できる

#### Acceptance Criteria

- **Given** 対話表示が完了している  
  **When** 画面下部に「入る」「サボる」のボタンが表示される  
  **Then** 片手親指でタップできる位置・サイズになっている

- **Given** ユーザーがどちらかをタップ  
  **When** 選択完了  
  **Then** 選択結果がDynamoDBに保存される(端末UUID、日時、選択内容、参照したヘルスケア要約、参照した天気要約、迷惑リスクレベル)

- **Given** 選択完了  
  **When** 画面遷移  
  **Then** 両キャラから選択を**全肯定する**短いメッセージが表示される(設計原則)

---

### US-3.2【M】★ サボり履歴のカレンダー表示

**As a** 振り返りをしたいユーザー  
**I want** 過去のサボり/入浴履歴がカレンダー形式で見える  
**So that** 自分の傾向を冷静に振り返れる

#### Acceptance Criteria

- カレンダー上で各日が「入った/サボった/未利用」の3状態で色分け表示される
- 月単位で前後にスクロール/スワイプで移動できる
- 任意の日をタップすると、その日の対話・選択・データ要約が見られる
- 全期間データを保持(NFR:無限保持)

#### 備考
- v4で連続サボりストリーク表示は削除されたが、**カレンダー表示は残す**(振り返り目的)
- 達成感を煽らない中立的な配色を採用(リスクR11対応:風呂キャン誘発を抑制)

## E4. 称号・バッジ

### US-4.1【M】 称号・バッジの自動付与

**As a** 蓄積を楽しみたいユーザー  
**I want** サボり実績に応じて自動で称号・バッジがもらえる  
**So that** 使い続けるモチベーションになる

#### Acceptance Criteria

- 選択保存時に、付与条件を満たす称号があるかチェックする
- 条件達成時、画面に「称号獲得!」のアニメーション/通知が表示される
- 獲得済み称号一覧が確認できる画面がある

#### 備考
- 称号付与ロジックはAchievement Unitの責務
- 条件はシンプルなルール(累計回数、特定パターン等)で定義し、Construction Phaseで詳細化

---

### US-4.2【M】 過激でユーモラスな称号セット(v4更新)

**As a** 楽しい体験を求めるユーザー  
**I want** 称号にユーモアと過激さのある名前がついていて「ダメ自慢」できる  
**So that** 自分のダメさをネタとして昇華できる

#### Acceptance Criteria

- 称号セットは**事前にリスト化されたもののみ**を使用する(LLM動的生成は禁止 / リスクR13対応)
- 称号一覧はデータ駆動で持ち、後から追加できる構造にする
- 最低**10種類**の称号を用意する。例:

| 称号名 | 付与条件 | 種別 |
|---|---|---|
| ダメ人間勲章 | 初サボり時 | 歓迎 |
| 悪魔の言いなり | 連続サボり7日 | 連続系 |
| サボりマスター | 累計サボり30回 | 累計系 |
| サボりセンセイ | 累計サボり100回 | 累計系 |
| 堕落貴族 | 累計サボり50回 | 過激系 |
| ぐうたら大臣 | 累計サボり200回 | 過激系 |
| ソファと一体化 | 同じ曜日に連続でサボり | パターン系 |
| 真夏のサボり貴族 | 気温30℃以上の日にサボった | 状況系 |
| 梅雨どきのサボりマスター | 雨の日に連続サボり3日 | 状況系 |
| 人類の希望 | 何らかの達成時(皮肉ネーミング) | 特殊 |

#### 備考
- 「迷える子羊」「天使の優等生」はv4で削除済み(健全すぎてテーマと逆方向)
- 称号は**品位の範囲内**でユーモラスを追求(差別的・下品にしない)

## E5. アプリ全体体験

### US-5.1【M】 オンボーディング

**As a** 初回起動のユーザー  
**I want** アプリのコンセプトが3〜4画面で説明される  
**So that** 安心して使い始められる

#### Acceptance Criteria

- 初回起動時のみ表示され、2回目以降はスキップ
- 天使と悪魔のキャラクター紹介を含む
- スキップ可能

---

### US-5.2【M】 ホーム画面

**As a** ソファで動けないユーザー  
**I want** アプリを開いたら最小タップで対話に入れる  
**So that** 動けない状態でも使える

#### Acceptance Criteria

- ホーム画面に「天使と悪魔に相談する」のメインボタンが目立つ位置にある
- 履歴・設定への遷移は副次的な配置
- v4の変更:**連続サボりストリーク表示はホーム画面に置かない**(誘発抑制)

---

### US-5.3【M】 設定画面

**As a** ユーザー  
**I want** 設定画面でデータ許可状況、キャラクター切替ができる  
**So that** 自分の状態を確認・調整できる

#### Acceptance Criteria

- ヘルスケア・位置情報の許可状態が表示される
- 各設定への導線がある
- アプリのバージョン情報が表示される

#### 備考
- v4の変更:履歴のエクスポート機能は削除

---

### US-5.5【M】★ コンセプト明示オンボーディング(新規 / v4対応 / リスクR12対応)

**As a** 初回起動のユーザー  
**I want** このアプリが「ふざけた、人をダラけさせるサービス」であることが明確に伝えられる  
**So that** 真剣な健康相談アプリと誤解せず、適切な期待値で使い始められる

#### Acceptance Criteria

- **Given** 初回起動である  
  **When** オンボーディング画面が表示される  
  **Then** 1画面目で「これは『人をダメにする』ためのおふざけアプリです」というコンセプトが明示される

- **Given** オンボーディング  
  **When** 進める  
  **Then** 「**真剣な健康相談には使わないでください**」という注意書きが含まれる

- **Given** オンボーディング  
  **When** 完了  
  **Then** 同意ボタン(「ダメ人間として進む」等のユーモラスな文言)をタップしないと先に進めない

#### 備考
- リスクR11(倫理的リスク)・R12(ユーザー層ミスマッチ)対応の中核
- 注意書きはユーモラスな文言で表現するが、**意味は真面目に伝わる**ようにする
- 設定画面からも再表示可能にする

---

### US-5.6【M】 ダラけ感のあるUI演出(新規 / v4対応)

**As a** ダラけたいユーザー  
**I want** UIそのものがダラけた雰囲気を醸し出している  
**So that** アプリを開いた瞬間からダラけ気分に入れる

#### Acceptance Criteria

- **Given** ホーム画面・対話画面・履歴画面  
  **When** 表示  
  **Then** 以下の演出のうち**最低3つ**が実装されている:
