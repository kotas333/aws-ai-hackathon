## E1. ヘルスケア・環境データ連携

### US-1.1【M】★ ヘルスケアデータの自動取得 — *FR-01, FR-02*

**As a** 疲弊した社会人ユーザー
**I want** アプリを開いたときに、ヘルスケアアプリの行動履歴 (歩数、運動時間、心拍数等) が自動的に読み込まれる
**So that** 動けないソファの上でも、追加入力なしに自分の状況を AI に伝えられる

#### Acceptance Criteria

- **Given** ユーザーが初回起動時にヘルスケアアクセスを許可している
  **When** ユーザーがアプリを開く
  **Then** 当日 0 時から現在までの歩数・アクティブエネルギー・運動時間・心拍数・睡眠時間・立ち上がり時間の **6 項目** が自動取得される
- **Given** ヘルスケアデータの取得に失敗した (権限拒否、API 障害等)
  **When** 取得処理が走る
  **Then** 「データ取得に失敗しました」のメッセージが表示され、ヘルスケアデータなしでも対話生成に進める (フォールバック)
- **Given** 当日のヘルスケアデータがゼロ (まだ何もしていない朝など)
  **When** 取得処理が走る
  **Then** ゼロ値として正常に処理され、ジャッジ悪魔の対話生成に渡される

#### 備考
- 取得項目は Intent v4 で確定済み (計 6 項目)
- ヘルスケア生データは **端末ローカルにのみ保持** し、AWS には送信しない (NFR-DAT-02 / リスク R3 対応)

---

### US-1.2【M】 ヘルスケアアクセス許可フロー — *FR-01*

**As a** 初回起動のユーザー
**I want** ヘルスケアアプリへのアクセス許可を、なぜ必要かの説明と共にリクエストされる
**So that** 安心してデータ提供できる

#### Acceptance Criteria

- **Given** 初回起動である
  **When** ヘルスケア許可ダイアログを出す前
  **Then** 事前説明画面で「ジャッジがデータを参照して話す」ことが説明される
- **Given** ユーザーが許可をすべて拒否した
  **When** アプリが起動する
  **Then** 「ヘルスケアなしでも遊べます (精度は落ちます)」と案内され、利用継続できる

---

### US-1.3【M】★ 位置情報と天気データの取得 — *FR-03*

**As a** ユーザー
**I want** 自分のいる地域の天気・気温が自動的に取得される
**So that** 「真夏の猛暑日」「梅雨どき」など環境を踏まえたジャッジの意見を聞ける

#### Acceptance Criteria

- **Given** ユーザーが位置情報利用を許可している
  **When** 対話生成リクエストの直前
  **Then** 現在地の気温 (℃)、天気 (晴れ/曇り/雨/雪等)、湿度が天気 API から取得される
- **Given** 位置情報が拒否されている、または天気 API 取得失敗
  **When** 対話生成リクエストの直前
  **Then** 環境データなしで対話生成に進める (フォールバック)

#### 備考
- 位置情報は **取得時のみ使用し永続保存しない** (プライバシー配慮 / NFR-DAT-02 / リスク R3 対応)
- 天気 API は無料枠のあるサービスを選定 (OpenWeatherMap 等)

---

### US-1.4【S】 取得データのプレビュー表示 — *FR-01, FR-03*

**As a** 透明性を求めるユーザー
**I want** ジャッジ悪魔が議論する前に、取得されたデータの要約を確認できる
**So that** 「何を根拠に話されているか」を理解できる

#### Acceptance Criteria

- 取得データのサマリー (歩数 ◯ 歩、気温 ◯℃ 等) が、対話表示の上部または別画面で確認できる
- データに納得いかない場合、対話生成前に「やり直し」ができる

---

### US-1.5【M】★ 迷惑リスク判定 (新規 / v4 対応) — *FR-04*

**As a** プロダクト
**I want** 取得したヘルスケアデータと環境データから「周囲への迷惑リスク」を判定し、フラグとして対話生成に渡す
**So that** 悪魔がリスク高時に柔らかく入浴を推奨する仕様 (US-2.4) を実現できる

#### Acceptance Criteria

- **Given** ヘルスケアデータと環境データが取得できている
  **When** 対話生成リクエストの直前
  **Then** 以下のプロキシ指標から複合条件で **迷惑リスクフラグ** を計算する:
  - 最終入浴からの経過時間 (72 時間超でリスク高方向)
  - 運動量 (歩数・運動時間・アクティブエネルギーの合算スコア)
  - 気温・天気 (夏場・湿度高時は閾値短縮)
  - 心拍数 (発汗量の推定)
- **Given** 計算結果
  **When** プロンプト構築
  **Then** リスクレベル (low / medium / high) と各指標の値がプロンプトに含まれる
- **Given** データが部分的に欠損している
  **When** 計算処理
  **Then** 取得できた指標のみで暫定スコアを算出し、欠損ありフラグを付ける

#### 備考
- 閾値の具体値は Construction Phase で詳細化
- LLM が最終判断するハイブリッド方式 (Intent v4 の健康配慮ポリシー)
- このストーリーは **Healthcare Integration Unit** ではなく独立した **Risk Assessment Unit** として扱う可能性あり (Unit 分解時に判断)
- **PBT 対象** (Partial 適用): プロキシ指標 → フラグ計算は純粋関数

---

### US-1.6【M】 カレンダー連携による翌日予定の対話反映 (新規 / AI-DLC v3 / Application Design Revision 2) — *FR-12*

**As a** 疲弊した社会人ユーザー
**I want** 翌日の予定の概要が対話に反映される
**So that** 「明日早起き」「明日休み」などの状況に応じた現実的な助言を受けられる

#### Acceptance Criteria

- **Given** ユーザーが iOS カレンダー (EventKit) アクセスを許可している
  **When** 対話生成リクエストの直前
  **Then** 翌日の予定サマリ (`isHoliday: bool` / `earliestEventTime: ISO 8601 string | null` / `eventCount: number`) が User Prompt に含まれる
- **Given** カレンダー権限拒否 / 取得失敗
  **When** 対話生成リクエスト
  **Then** カレンダー情報なし (全フィールド null) で対話生成が継続される (フォールバック)
- **Given** カレンダー生情報 (タイトル / 場所 / 参加者)
  **When** どのような時点でも
  **Then** 端末ローカルから外に出ない (NFR-DAT-02 / R3 / SECURITY-13 の延長)。AWS には集計値のみ送信

#### 備考
- iOS EventKit のみと連携 (Google / iCloud / Outlook 等は iOS のアカウント追加で同期しておけば EventKit 経由で読める / Google API 等の直接連携は行わない / NFR-DAT-03 と整合)
- 機微データ境界の延長は HealthSummary パターンと完全に同じ思想
- 詳細は `application-design.md` Section 9 (User Prompt 構造) と Section 10 (機微データフロー)

## E2. ジャッジと悪魔の対話

### US-2.1【M】★ ジャッジと悪魔の対話メッセージ生成 (v4 更新) — *FR-05, FR-06*

**As a** ソファで動けないユーザー
**I want** ジャッジと悪魔がデータを根拠に対話してくれる
**So that** 自分で判断する代わりに、二人の議論を眺めて気持ちを整理できる

#### Acceptance Criteria

- **Given** ヘルスケアデータ・環境データ・迷惑リスクフラグが揃っている
  **When** 対話生成リクエストが送られる
  **Then** Amazon Bedrock に対し、データ・キャラクター設定・原則・リスクフラグを含むプロンプトが送信され、ジャッジと悪魔の対話形式メッセージが返ってくる
- **Given** Bedrock からの応答
  **When** 画面に表示する
  **Then** ジャッジと悪魔のメッセージがそれぞれ識別可能な形 (アイコン、色、左右配置等) で交互に表示される
- **Given** Bedrock からの応答
  **When** 表示完了
  **Then** **悪魔の発言が必ず最後に来る** (設計原則の厳守)
- **Given** Bedrock からの応答
  **When** 表示
  **Then** どちらのキャラもユーザーを真剣に責める表現は含まない (プロンプト設計で担保)
- **Given** **基本トーン**
  **When** 通常時の対話
  **Then** 悪魔は積極的にダラけ・サボりを推奨する (v4 の「振り切り」方向)
- **Given** ネットワークエラー、Bedrock 障害
  **When** リクエスト失敗
  **Then** 「ちょっと考え事してます…」等のフォールバック表示と再試行ボタンを出す

#### 備考
- プロンプト設計は Domain Model の中心 (Construction Phase で詳細詰め)
- リスク R4・R7・R14 対応: プロンプトのテストを早期に実施
- 応答時間は NFR-USA-02「数秒以内」目標、超過時はローディング表示
- **PBT 対象** (Partial 適用): 綺麗度判定の入力組み立て (LLM 入力構築) は純粋関数

---

### US-2.2【M】 対話のターン数 — *FR-06*

**As a** 短時間で済ませたいユーザー
**I want** 対話が長すぎず短すぎないターン数で完結する
**So that** 2〜3 分の利用時間に収まる

#### Acceptance Criteria

- 対話のターン数は **4〜6 ターン** (ジャッジ→悪魔→ジャッジ→悪魔→…) を目安とする
- 全ターンを生成・表示するのに 5 秒以内を目標とする
- ストリーミング表示 (キャラごとに順次表示) も可とする

---

### US-2.3【S】 キャラクターの口調を選べる — *FR-06*

**As a** 自分好みの体験をしたいユーザー
**I want** ジャッジ悪魔の口調・人格をいくつかのプリセットから選べる
**So that** 飽きずに使い続けられる

#### Acceptance Criteria

- ジャッジと悪魔のペアとして、**最低 2 セット** のプリセットを用意 (例: 標準セット、関西弁セット)
- 設定画面でペアを切り替え可能
- 切り替え後は次回の対話生成からプロンプトに反映される

#### 備考
- MVP では「標準セット」のみで動かしてもよい

---

### US-2.4【M】★ 悪魔の発言トーンシフト (新規 / v4 対応) — *FR-07*

**As a** 過度なサボりで健康を損ないかけているユーザー
**I want** 連続サボりが長期化した時や、迷惑リスクが高まった時に、悪魔のトーンが柔らかく健康寄りにシフトする
**So that** 自分のサボりパターンに気づき、必要に応じて入浴できる

#### Acceptance Criteria

- **Given** 連続サボり長期化を **綺麗度の悪化度合い** で検知 (データ駆動)
  **When** 対話生成リクエスト
  **Then** プロンプトに「連続サボり長期化フラグ」が付与され、悪魔の発言が穏やかな健康寄りトーンになる (例: 「最近お風呂入ってないっぽいけど大丈夫?」)
- **Given** 迷惑リスクフラグが `high` (US-1.5)
  **When** 対話生成リクエスト
  **Then** プロンプトにリスクフラグが付与され、悪魔も柔らかく入浴を推奨する (例: 「さすがに今日は入っといた方がいいよ、明日仕事でしょ?」)
- **Given** トーンシフト発動時でも
  **When** 対話生成
  **Then** 悪魔は「ジャッジのような厳しい説教」はしない。**あくまで柔らかい・甘やかし口調を保ちながら、内容として健康寄りにシフト** する
- **Given** ユーザーが結果として「サボる」を選んだ
  **When** 選択完了
  **Then** トーンシフト発動時でも、悪魔は最終的にユーザーの選択を肯定する

#### 備考
- このストーリーは Intent v4 の健康配慮ポリシーの中核
- リスク R14 対応: プロンプト設計が複雑になるため、Bolt で段階的に導入
- トーンシフトの発動条件・閾値は Construction Phase で詳細化

## E3. 選択と履歴

### US-3.1【M】 入る/サボるの選択 — *FR-08*

**As a** 議論を聞き終えたユーザー
**I want** 「入る」「サボる」のボタンをタップして選択する
**So that** 自分の意思を記録できる

#### Acceptance Criteria

- **Given** 対話表示が完了している
  **When** 画面下部に「入る」「サボる」のボタンが表示される
  **Then** 片手親指でタップできる位置・サイズになっている (NFR-USA-01)
- **Given** ユーザーがどちらかをタップ
  **When** 選択完了
  **Then** 選択結果が DynamoDB に保存される (端末 UUID、日時、選択内容、参照したヘルスケア要約、参照した天気要約、迷惑リスクレベル)
- **Given** 選択完了
  **When** 画面遷移
  **Then** 両キャラから選択を **全肯定する** 短いメッセージが表示される (設計原則)

---

### US-3.2【M】★ サボり履歴のカレンダー表示 — *FR-09*

**As a** 振り返りをしたいユーザー
**I want** 過去のサボり/入浴履歴がカレンダー形式で見える
**So that** 自分の傾向を冷静に振り返れる

#### Acceptance Criteria

- カレンダー上で各日が「入った/サボった/未利用」の 3 状態で色分け表示される
- 月単位で前後にスクロール/スワイプで移動できる
- 任意の日をタップすると、その日の対話・選択・データ要約が見られる
- 全期間データを保持 (NFR-DAT-01: 無限保持)

#### 備考
- v4 で連続サボりストリーク表示は削除されたが、**カレンダー表示は残す** (振り返り目的)
- 達成感を煽らない中立的な配色を採用 (リスク R11 対応: 風呂キャン誘発を抑制)

### US-3.3【S】 30 分後の入浴達成確認通知 (新規 / AI-DLC v3 / Application Design Revision 2) — *FR-14*

> **注**: v1 にあった同 ID (連続サボりストリーク表示 / v2 で削除済み) とは別ストーリー。**本ファイルでは v3 の US-3.3 (達成確認通知) のみを参照対象**。

**As a** 「お風呂に入る」と決意したユーザー
**I want** 30 分後に確認通知を受け取る
**So that** 自分が決意倒れだったかを認識できる (それ自体がサボりネタとして昇華される体験)

#### Acceptance Criteria

- **Given** ユーザーが `choice='bath'` を選択し、通知許可も得ている
  **When** 選択完了
  **Then** 決意完了から 30 分後に iOS ローカル通知 (UNUserNotificationCenter) が発火する
- **Given** 通知が表示される
  **When** 表示
  **Then** 文言は **悪魔キャラ寄りのトーン** (例: 「30 分経ったよ。本当にお風呂入った? まだソファで動けないでしょ笑」 / 詳細文言は Functional Design)
- **Given** 通知から「Yes (入った)」「まだ (入ってない)」を選択
  **When** 選択完了
  **Then** `POST /selections/{selectionId}/achievement` が呼ばれ、`achieved: bool` が DynamoDB の SelectionRecord に記録される
- **Given** ユーザーが「まだ」を選択した場合
  **When** 記録
  **Then** **元の `choice='bath'` 記録は維持** されたまま、`achieved: false` として記録される (達成失敗してもサボりとして上書きしない)
- **Given** `choice='skip'` を選択した場合
  **When** 選択完了
  **Then** 通知は **発火しない**

#### 備考
- 通知許可 (UNUserNotificationCenter) の権限フローを **オンボーディングに追加**
- アプリがフォアグラウンドの場合の挙動など通知方式の詳細は Functional Design で再検討する余地あり
- 称号関連の追加 (「決意倒れマスター」など) は本ストーリーではスコープ外。実装余裕があれば PRFAQ または Functional Design 後の Bolt で検討
- DDB SelectionRecord に `achieved: bool | null` フィールド追加 (null = 未確認 / true = 達成 / false = 未達)

## E4. 称号・バッジ

### US-4.1【M】 称号・バッジの自動付与 — *FR-10*

**As a** 蓄積を楽しみたいユーザー
**I want** サボり実績に応じて自動で称号・バッジがもらえる
**So that** 使い続けるモチベーションになる

#### Acceptance Criteria

- 選択保存時に、付与条件を満たす称号があるかチェックする
- 条件達成時、画面に「称号獲得!」のアニメーション/通知が表示される
- 獲得済み称号一覧が確認できる画面がある

#### 備考
- 称号付与ロジックは Achievement Unit の責務
- 条件はシンプルなルール (累計回数、特定パターン等) で定義し、Construction Phase で詳細化
- **PBT 対象** (Partial 適用): 称号付与の条件評価は純粋関数

---

### US-4.2【M】 過激でユーモラスな称号セット (v4 更新) — *FR-10*

**As a** 楽しい体験を求めるユーザー
**I want** 称号にユーモアと過激さのある名前がついていて「ダメ自慢」できる
**So that** 自分のダメさをネタとして昇華できる

#### Acceptance Criteria

- 称号セットは **事前にリスト化されたもののみ** を使用する (LLM 動的生成は禁止 / リスク R13 対応)
- 称号一覧はデータ駆動で持ち、後から追加できる構造にする
- 最低 **10 種類** の称号を用意する。例:

| 称号名 | 付与条件 | 種別 |
|---|---|---|
| ダメ人間勲章 | 初サボり時 | 歓迎 |
| 悪魔の言いなり | 連続サボり 7 日 | 連続系 |
| サボりマスター | 累計サボり 30 回 | 累計系 |
| サボりセンセイ | 累計サボり 100 回 | 累計系 |
| 堕落貴族 | 累計サボり 50 回 | 過激系 |
| ぐうたら大臣 | 累計サボり 200 回 | 過激系 |
| ソファと一体化 | 同じ曜日に連続でサボり | パターン系 |
| 真夏のサボり貴族 | 気温 30℃ 以上の日にサボった | 状況系 |
| 梅雨どきのサボりマスター | 雨の日に連続サボり 3 日 | 状況系 |
| 人類の希望 | 何らかの達成時 (皮肉ネーミング) | 特殊 |

#### 備考
- 「迷える子羊」「ジャッジの優等生」は v4 で削除済み (健全すぎてテーマと逆方向)
- 称号は **品位の範囲内** でユーモラスを追求 (差別的・下品にしない / NFR-CON-03)

## E5. アプリ全体体験

### US-5.1【M】 オンボーディング — *NFR-CON-04 補助*

**As a** 初回起動のユーザー
**I want** アプリのコンセプトが 3〜4 画面で説明される
**So that** 安心して使い始められる

#### Acceptance Criteria

- 初回起動時のみ表示され、2 回目以降はスキップ

- スキップ可能

### US-5.2【M】 ホーム画面 — *NFR-USA-01*

**As a** ソファで動けないユーザー
**I want** アプリを開いたら最小タップで対話に入れる
**So that** 動けない状態でも使える

- ホーム画面に「ジャッジと悪魔に相談する」のメインボタンが目立つ位置にある
- 履歴・設定への遷移は副次的な配置
- v4 の変更: **連続サボりストリーク表示はホーム画面に置かない** (誘発抑制)

### US-5.3【M】 設定画面

**As a** ユーザー
**I want** 設定画面でデータ許可状況、キャラクター切替ができる
**So that** 自分の状態を確認・調整できる

#### Acceptance Criteria

- ヘルスケア・位置情報の許可状態が表示される
- 各設定への導線がある
- アプリのバージョン情報が表示される

#### 備考
- v4 の変更: 履歴のエクスポート機能は削除

### US-5.5【M】★ コンセプト明示オンボーディング (新規 / v4 対応 / リスク R12 対応) — *NFR-CON-04*

**As a** 初回起動のユーザー
**I want** このアプリが「ふざけた、人をダラけさせるサービス」であることが明確に伝えられる
**So that** 真剣な健康相談アプリと誤解せず、適切な期待値で使い始められる

#### Acceptance Criteria

- **Given** 初回起動である
  **When** オンボーディング画面が表示される
  **Then** 1 画面目で「これは『人をダメにする』ためのおふざけアプリです」というコンセプトが明示される
- **Given** オンボーディング
  **When** 進める
  **Then** 「**真剣な健康相談には使わないでください**」という注意書きが含まれる
- **Given** オンボーディング
  **When** 完了
  **Then** 同意ボタン (「ダメ人間として進む」等のユーモラスな文言) をタップしないと先に進めない

#### 備考
- リスク R11 (倫理的リスク)・R12 (ユーザー層ミスマッチ) 対応の中核
- 注意書きはユーモラスな文言で表現するが、**意味は真面目に伝わる** ようにする
- 設定画面からも再表示可能にする

---

### US-5.6【M】 ダラけ感のある UI 演出 (新規 / v4 対応) — *FR-11, NFR-USA-03*

**As a** ダラけたいユーザー
**I want** UI そのものがダラけた雰囲気を醸し出している
**So that** アプリを開いた瞬間からダラけ気分に入れる

#### Acceptance Criteria

- **Given** ホーム画面・対話画面・履歴画面
  **When** 表示
  **Then** 以下の演出のうち **最低 3 つ** が実装されている:
  - ジャッジ悪魔のキャラクターがソファに沈み込んでいる/だらんとしている
  - アニメーションがぬるっとしている (イージング: ease-in-out をゆっくりめに)
  - フォントがゆるい・手書き風・丸みのあるもの
  - ローディング中にダラけたモーション (伸びをする、寝そべる等)
  - ボタンのタップフィードバックが「ぼよん」とした柔らかい動き

#### 備考
- リスク R13 対応: 演出は事前デザインを行い、過剰な刺激にならないよう配慮
- 具体的なデザインは Construction Phase で詳細化
- v4 で新規追加された主要な NFR/演出要件

---

### US-5.7【S】 翌日予定のホーム画面ミニ表示 (新規 / AI-DLC v3 / Application Design Revision 2) — *FR-13*

**As a** ユーザー
**I want** ホーム画面で翌日の予定をミニ表示で確認できる
**So that** 入浴判断の現実的な材料を見ながら決意できる

#### Acceptance Criteria

- **Given** カレンダー権限が許可されており、翌日に予定がある
  **When** ホーム画面表示
  **Then** **画面の片隅に最早開始時刻と件数が表示** される (例: 「明日 09:00〜・3 件」)
- **Given** 翌日が休日 (終日イベントが「休日」を示す等) または予定なし
  **When** ホーム画面表示
  **Then** 「明日は予定なし」のような表示になる
- **Given** ミニ表示をタップ
  **When** タップ
  **Then** **iOS 標準カレンダーアプリに遷移** する (アプリ内に詳細画面は持たない)
- **Given** カレンダー権限拒否 / 取得失敗
  **When** ホーム画面表示
  **Then** ミニ表示は表示されない (代替メッセージは出さない / 画面ノイズを避ける)

#### 備考
- アプリ内に詳細画面を持たないため、iOS 標準カレンダーアプリへの遷移経路を確保
- US-1.6 と同じ EventKit 経由の取得を再利用 (重複取得を避けるためキャッシュ戦略は Functional Design で確定)
- ホーム画面 (US-5.2) のレイアウトを邪魔しない控えめな配置
