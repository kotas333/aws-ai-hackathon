# 風呂キャンサポーター — Intent 定義

> **作成日**: 2026-05-05
> **状態**: 最終確定版

---

## Intent 文 (高レベルな目的)

> **「仕事に疲弊した 20 代社会人を、帰宅後のソファ/ベッドの上でとことんダラけさせるサポーター。"ジャッジ" と "悪魔" がヘルスケアデータと環境データを根拠に対話し、ユーザーがどんなにサボっても基本は全肯定し続ける。ただし周囲に迷惑が及ぶラインは超えないよう、悪魔自身もそこは諭す。サボった日々は "サボり資産" として永続蓄積され、ユーザーを罪悪感なくダメでいられる人間へと変えていく。」**

---

## プロダクトの設計哲学 (振り切り × バランスの中間)

### 振り切る方向
- 悪魔は積極的にダラけ・サボりを推奨
- 称号は「堕落貴族」「ぐうたら大臣」等、過激でユーモラス
- UI はダラけ感のある演出 (ぬるっと動く、ソファに沈み込む、ゆるいフォント等)
- サボりは「勲章」として誇示できる仕掛け

### バランス側 (品位を保つ)
- ユーザーを真剣に責めない、過度に煽らない
- 過激称号も **ユーモアの範囲** に留める (差別的・下品にしない)
- **周囲に迷惑が及ぶラインは守る** (健康配慮ポリシー参照)
- 真剣に健康相談を求めるユーザーが誤って傷つかないよう、オンボーディングでコンセプトを明示

---

## 健康配慮ポリシー

### 基本方針
**「実社会で周囲に迷惑がかからない範囲では、サボりを推奨してよい」**

### 「迷惑」の定義 (プロキシ指標)
アプリは現実世界を直接観測できないため、以下のプロキシで推定する:
- 最終入浴からの経過時間 (72 時間超でニオイリスク高と推定)
- 運動量 (歩数・運動時間・アクティブエネルギー / METs ベースで定量化)
- 気温・天気 (夏場・湿度高時は閾値を短く)
- 心拍数 (発汗量の推定)

### 実装方式 (システム側閾値計算 + LLM 最終判断のハイブリッド)
- システム側で **閾値フラグ** を計算 (例: `high_smell_risk: true`)
- 閾値フラグをプロンプトに含めて Bedrock に渡す
- 最終的な対話生成・トーン調整は LLM が判断
- LLM は「周囲に迷惑が及ぶ複合条件発動時は、悪魔も柔らかく入浴を推奨せよ」というシステムプロンプトを持つ

---

## ペルソナ

- 20 代社会人
- 仕事で疲弊しサボりがち
- 帰宅後にソファ/ベッドで動けなくなる
- 風呂をサボることへの罪悪感を抱えている
- ユーモアと自虐が好き、「ダメな自分」をネタにできる感性

---

## コア体験 (2〜3 分の利用)

1. アプリを開く (片手・最小タップ、ダラけた UI)
2. ホーム画面中央のスキャンボタンを押す (儀式的な 1 タップ / US-5.2 第 1 段階)
3. スキャン中のローディング演出 (キャラがソファに沈む等 / 数秒 / FR-11 / NFR-USA-03)
4. ヘルスケアデータ + 環境データの取得・迷惑リスク判定・対話生成が実行される
5. **ジャッジと悪魔がデータを根拠に対話する形でメッセージが表示される** (US-5.2 第 2 段階)
6. ユーザーが「入る」「サボる」を選択
7. 選択は履歴として永続蓄積され、過激でユーモラスな称号・バッジが付与される
8. **どちらを選んでも両キャラから肯定される** (ただし状況により悪魔の発言トーンは変化)

## 二人のキャラクター (コア・ドメイン)

### ジャッジ (データ駆動アナリスト / 旧称: 天使)
- ヘルスケアデータ + 天気・気温を根拠に淡々と状況を提示する **無機質寄りの判定者**
- データを根拠に説明する / 感情的にならない
- ユーザーを責めない / 過剰な健康指導をしない
- 悪魔との対比は **「無機質な判定者 vs. 人格的な誘惑者」**
- **役割**: ユーザーに健康側の現実を客観的に提示する視点

### 悪魔 (サボり推奨側のアドバイザー)
- **基本トーン**: 積極的にダラけ・サボりを推奨
- **甘やかし型**: 「いいよいいよ、寝ちゃおう」「もう湯船とか沸かすの面倒でしょ」
- ユーザーを責めない、疲れを労わる友人

#### 悪魔の発言シフト仕様

| 状況 | 悪魔のトーン |
|---|---|
| 通常時 | 積極的にサボりを推奨 (基本形) |
| **連続サボり長期化検知時** | データ駆動で判定し、トーンを穏やかな健康寄りにシフト。「最近お風呂入ってないっぽいけど大丈夫?」 |
| **周囲迷惑リスク高検知時** | 複合条件で判定し、悪魔自身も柔らかく入浴を推奨。「さすがに今日は入っといた方がいいよ、明日仕事でしょ?」 |

連続サボりの判定はデータ駆動 (綺麗度悪化の度合いで判定)。
迷惑リスクの判定は複合条件 (最終入浴日数 + 運動量 + 気温の組み合わせ)。

### 二人の設計原則
- 両キャラとも「ユーザーの味方」
- **悪魔が常に最後の発言権** (基本構造を維持)
- ユーザーが選択した後は、両キャラとも全肯定
- 綺麗度判定の精度の粗さは仕様内のユーモアとして機能
- **二人構造を維持** (第三キャラは追加しない / NFR-USA-01 整合)

## 主要機能 (MVP ライン: 全て動かす)

| 機能 | 内容 |
|---|---|
| ヘルスケア連携 | iOS HealthKit (Q4 確定) |
| 取得項目 (計 6 種) | 歩数、アクティブエネルギー、運動時間、心拍数、睡眠時間、立ち上がり時間 |
| 天気・気温連携 | 位置情報 → 天気 API (無料サービス) |
| **迷惑リスク閾値判定** | プロキシ指標を計算し、フラグ化して LLM に渡す |
| 綺麗度判定 | LLM 判断型: ヘルスケア + 天気 + 迷惑リスクフラグを Bedrock に渡し定性判定 |
| ジャッジ・悪魔対話生成 | Amazon Bedrock (Claude) による二者対話形式メッセージ生成 |
| **悪魔の発言シフト** | 連続サボり長期化時・迷惑リスク高時の動的シフト |
| 選択の記録 | 「入る」「サボる」を DynamoDB に保存 |
| サボり履歴 | 全期間データ、カレンダー表示 |
| 称号・バッジ | **過激でユーモラスな称号セット** |
| **ダラけ感のある UI 演出** | キャラがソファに沈む、ぬるっと動く、ゆるいフォント等 |

### MVP から削除した項目

- ~~連続サボりストリーク表示~~ — 風呂キャン誘発リスクのため削除
- ~~履歴のエクスポート機能~~ — スコープ外と判断
- ~~ダークモード対応~~ — 本プロダクトのスコープ外

## 称号セット

過激でユーモラス。「ダメ自慢できる」方向に振り切る。事前リスト化したもののみを使用 (LLM 動的生成は禁止)。

### 継続採用の称号
- 「悪魔の言いなり」(連続サボり 7 日)
- 「サボりマスター」(累計サボり 30 回)
- 「サボりセンセイ」(累計サボり 100 回)
- 「真夏のサボり貴族」(気温 30℃ 以上の日にサボった)
- 「梅雨どきのサボりマスター」(雨の日に連続サボり 3 日)

### 過激路線で追加する称号
- 「**堕落貴族**」(累計サボり 50 回)
- 「**ぐうたら大臣**」(累計サボり 200 回)
- 「**ソファと一体化**」(同じ曜日に連続でサボり)
- 「**人類の希望**」(皮肉ネーミング、何らかの達成時)
- 「**ダメ人間勲章**」(初サボり時の歓迎称号)

### 採用しない称号 (検討段階で削除)
- ~~「迷える子羊」~~ — 健全すぎてテーマと逆方向
- ~~「ジャッジの優等生」~~ — 健全すぎてテーマと逆方向 (旧名: 天使の優等生)
- ~~「初サボり」~~ — 「ダメ人間勲章」に統合

## 技術スタック

| 層 | サービス |
|---|---|
| LLM | Amazon Bedrock (Claude Sonnet 4.6 第一候補 / Claude Opus 4.7 拡張可能) |
| API | API Gateway + Lambda |
| DB | DynamoDB (シンプル構成、余裕があればローカルキャッシュ追加) |
| 認証 | 端末 UUID ベースの軽量識別 |
| デプロイ | CloudFormation または CDK |
| 監視 | CloudWatch |
| 外部 API | 天気 API (OpenWeatherMap 等)、HealthKit、EventKit、UNUserNotificationCenter |
| リージョン | ap-northeast-1 (Tokyo) |
| プラットフォーム | **iOS のみ確定** (Q4 = A / Swift / SwiftUI) / 撤退ルートは iOS DEBUG ビルド擬似データモード |

## 非機能要件 (NFR)

### 操作性
- 片手操作・最小タップで完結
- 応答速度: 対話生成は数秒以内
- ダラけ感のある演出

### データ
- データ永続性: 履歴は無限保持
- プライバシー重視: ヘルスケア生データ + カレンダー生情報はローカル限定、サボり履歴のみ AWS に保存
- AWS マネージドサービスのみで構築
- 日本語のみ対応

### コンセプト/トーン
- ユーザーを真剣に責めない
- 過剰な健康指導をしない
- 称号・対話のユーモアは品位の範囲内
- 真面目な健康相談を求めるユーザーが誤って使った場合の安全性を確保 (オンボーディングでコンセプト明示)

---

## やらないこと (スコープ外)

- クラウド「同期」(複数端末でのデータ共有)
- シェア機能 (SNS シェア・他者交流)
- 複数言語対応
- プッシュ通知 (リモート / APNS)。決意 30 分後の達成確認のみ iOS ローカル通知を使用
- 課金・課金要素
- 他サービス連携 (LINE、Slack 等)
- 連続サボりストリーク表示 (誘発リスク回避)
- 履歴のエクスポート機能
- ダークモード対応

## リスク (Risk Register)

| # | リスク | 重要度 | 対策方針 |
|---|---|---|---|
| R1 | フル API 連携 + 二者対話 + 蓄積要素 + 発言シフト = スコープ過大 | **高** | MVP ラインから絶対に下げない |
| R2 | ヘルスケア API 連携の実装難易度・申請コスト | 高 | プラットフォーム選択時に実装力で判断、最悪は擬似データへ撤退 |
| R3 | 機微情報 (ヘルスケア・位置情報・カレンダー) の取り扱い | 高 | ローカル保存基本、AWS 送信は最小限 |
| R4 | LLM 応答の品質・安全性 | 中 | プロンプト設計、両キャラがユーザーを責めないことの徹底 |
| R5 | プラットフォーム判断の遅延 | 中 → 解消 | iOS のみで Q4 確定 |
| R6 | 「綺麗度」「迷惑リスク」の定義の曖昧さ | 中 | LLM 判断型のプロンプト設計で吸収、対話のユーモアに転化 |
| R7 | ジャッジがうるさく感じられるリスク | 中 | 悪魔が最後の発言権、選択後は両キャラ肯定の原則を厳守 |
| R8 | AWS アカウント・権限準備の遅延 | **高** | Bolt 1 のクリティカルパスとして完了させる |
| R9 | Bedrock のモデルアクセス申請 | 中 | Bolt 1 で一緒に対応 |
| R10 | LLM 呼び出し料金の予算超過 | 低 | 1 日のリクエスト上限を実装、CloudWatch で監視 |
| **R11** | **倫理的リスク**: 「サボりを助長する」批判への備え | **中** | 「周囲への迷惑ライン」を超えない設計、デモ説明での前置き、オンボーディングでコンセプト明示 |
| **R12** | **ユーザー層のミスマッチ**: 真剣な健康相談を求める層が誤って使うリスク | **中** | オンボーディングでコンセプト・キャラクター紹介を明確に行う |
| **R13** | **称号過激化の暴走**: 称号が下品/差別的になるリスク | **中** | 称号は事前リスト化し、レビュー済みのもののみ使用。LLM に動的生成させない |
| **R14** | **発言シフト仕様の複雑化**: プロンプト設計が複雑になり、応答品質が落ちる | 中 | プロンプトテストを早期に実施、Bolt で段階導入 |

## Differentiators (主要差別化要因)

- **逆方向のヘルステックアプリ**: 健康促進アプリの真逆を行く「ダラけさせる」コンセプト
- **テーマとの整合**: 「人をダメにするサービス」を真正面から表現
- **ジャッジと悪魔の対話**: AI ネイティブ時代ならではのインタラクション
- **本物の行動データ + 天気** を根拠にジャッジの判定にリアリティを持たせる
- **動的な悪魔の発言シフト**: データ駆動で人格が変化する LLM 活用の高度な事例
- **永続蓄積 × 過激な称号** で「ダメ自慢」できるリピート性
- **AWS マネージドサービスでの構築** (Bedrock + Lambda + DynamoDB + API Gateway + S3 + CloudFront)

## プロダクト名の検討 (暫定)

候補と評価:

| 候補 | 評価 |
|---|---|
| 風呂キャンサポーター (現行) | ややニュートラル、「ダメにする」テーマとの結びつきが弱い |
| 風呂キャンコンシェルジュ | 上品な響きとダラけたサービスのギャップが面白い |
| **ダラ風呂** | 短く覚えやすい、ダラけ感あり、ユーモラス |
| ダメ風呂サポーター | ストレートだが直接的すぎるかもしれない |
| サボりっぽ | サボることに対する愛称的な響き |
| 入らんぼ | 「サボり」をひらがなにして柔らかさを出す |
| キャン部 | 「風呂キャン部活動」のような共同体感、ただし共有機能はスコープ外 |

**推奨**: 「**ダラ風呂**」または「**風呂キャンコンシェルジュ**」

ただし、最終的なプロダクト名はチームで決定してもよい。本 Intent 定義は「**風呂キャンサポーター**」のまま進めても、後段の影響は小さい。
