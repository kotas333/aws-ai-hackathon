## Intent文(高レベルな目的)

> **「仕事に疲弊した20代社会人を、帰宅後のソファ/ベッドの上でとことんダラけさせるサポーター。"天使"と"悪魔"がヘルスケアデータと環境データを根拠に対話し、ユーザーがどんなにサボっても基本は全肯定し続ける。ただし周囲に迷惑が及ぶラインは超えないよう、悪魔自身もそこは諭す。サボった日々は"サボり資産"として永続蓄積され、ユーザーを罪悪感なくダメでいられる人間へと変えていく。」**

## プロダクトの設計哲学(振り切り×バランスの中間)

### 振り切る方向(GG/HH/II採用)
- 悪魔は積極的にダラけ・サボりを推奨
- 称号は「堕落貴族」「ぐうたら大臣」等、過激でユーモラス
- UIはダラけ感のある演出(ぬるっと動く、ソファに沈み込む、ゆるいフォント等)
- サボりは「勲章」として誇示できる仕掛け

### バランス側(品位を保つ)
- ユーザーを真剣に責めない、過度に煽らない
- 過激称号も**ユーモアの範囲**に留める(差別的・下品にしない)
- **周囲に迷惑が及ぶラインは守る**(質問5の基準)
- 真剣に健康相談を求めるユーザーが誤って傷つかないよう、オンボーディングでコンセプトを明示

## 健康配慮ポリシー(質問4・5の確定事項)

### 基本方針
**「実社会で周囲に迷惑がかからない範囲では、サボりを推奨してよい」**

### 「迷惑」の定義(プロキシ指標)
アプリは現実世界を直接観測できないため、以下のプロキシで推定する:
- 最終入浴からの経過時間(72時間超でニオイリスク高と推定)
- 運動量(歩数・運動時間・アクティブエネルギー)
- 気温・天気(夏場・湿度高時は閾値を短く)
- 心拍数(発汗量の推定)

### 実装方式(質問1・6・7のハイブリッド)
- システム側で**閾値フラグ**を計算(例:`high_smell_risk: true`)
- 閾値フラグをプロンプトに含めてBedrockに渡す
- 最終的な対話生成・トーン調整はLLMが判断
- LLMは「周囲に迷惑が及ぶ複合条件発動時は、悪魔も柔らかく入浴を推奨せよ」というシステムプロンプトを持つ

## ペルソナ

- 20代社会人
- 仕事で疲弊しサボりがち
- 帰宅後にソファ/ベッドで動けなくなる
- 風呂をサボることへの罪悪感を抱えている
- ユーモアと自虐が好き、「ダメな自分」をネタにできる感性

---

## コア体験(2〜3分の利用)

1. アプリを開く(片手・最小タップ、ダラけたUI)
2. ヘルスケアデータと天気・気温が自動取得される
3. システムが「周囲への迷惑リスク」フラグを計算
4. **天使と悪魔がデータを根拠に対話する形でメッセージが表示される**
5. ユーザーが「入る」「サボる」を選択
6. 選択は履歴として永続蓄積され、過激でユーモラスな称号・バッジが付与される
7. **どちらを選んでも両キャラから肯定される**(ただし状況により悪魔の発言トーンは変化)

## 二人のキャラクター(コア・ドメイン)

### 天使(健康側のアドバイザー)
- ヘルスケアデータ+天気・気温を根拠に判定
- 優しく諭す、データを根拠に説明
- ユーザーを責めない、健康を心配する友人としての立場
- **役割**: ユーザーを健康側に引っ張る現実的視点

### 悪魔(サボり推奨側のアドバイザー)
- **基本トーン**: 積極的にダラけ・サボりを推奨(GG)
- **甘やかし型**:「いいよいいよ、寝ちゃおう」「もう湯船とか沸かすの面倒でしょ」
- ユーザーを責めない、疲れを労わる友人

#### 悪魔の発言シフト仕様(質問2 E+F)

| 状況 | 悪魔のトーン |
|---|---|
| 通常時 | 積極的にサボりを推奨(基本形) |
| **連続サボり長期化検知時(F)** | データ駆動で判定し、トーンを穏やかな健康寄りにシフト。「最近お風呂入ってないっぽいけど大丈夫?」 |
| **周囲迷惑リスク高検知時(E)** | 複合条件で判定し、悪魔自身も柔らかく入浴を推奨。「さすがに今日は入っといた方がいいよ、明日仕事でしょ?」 |

連続サボりの判定はデータ駆動(綺麗度悪化の度合いで判定)。
迷惑リスクの判定は複合条件(最終入浴日数+運動量+気温の組み合わせ)。

### 二人の設計原則
- 両キャラとも「ユーザーの味方」
- **悪魔が常に最後の発言権**(基本構造を維持)
- ユーザーが選択した後は、両キャラとも全肯定
- 綺麗度判定の精度の粗さは仕様内のユーモアとして機能
- **二人構造を維持**(第三キャラは追加しない / 質問10 AA採用)

## 主要機能(MVPライン:全て動かす)

| 機能 | 内容 |
|---|---|
| ヘルスケア連携 | iOS HealthKit / Android Health Connect |
| 取得項目(計6種) | 歩数、アクティブエネルギー、運動時間、心拍数、睡眠時間、立ち上がり時間 |
| 天気・気温連携 | 位置情報 → 天気API(無料サービス) |
| **迷惑リスク閾値判定** | プロキシ指標を計算し、フラグ化してLLMに渡す(新規) |
| 綺麗度判定 | LLM判断型:ヘルスケア+天気+迷惑リスクフラグをBedrockに渡し定性判定 |
| 天使・悪魔対話生成 | Amazon Bedrock(Claude)による二者対話形式メッセージ生成 |
| **悪魔の発言シフト** | 連続サボり長期化時・迷惑リスク高時の動的シフト(新規) |
| 選択の記録 | 「入る」「サボる」をDynamoDBに保存 |
| サボり履歴 | 全期間データ、カレンダー表示 |
| 称号・バッジ | **過激でユーモラスな称号セット**(再構成) |
| **ダラけ感のあるUI演出** | キャラがソファに沈む、ぬるっと動く、ゆるいフォント等(新規) |

## 技術スタック(AWS主催前提 / v3から変更なし)

| 層 | サービス |
|---|---|
| LLM | Amazon Bedrock(Claude 3.5 Sonnet等) |
| API | API Gateway + Lambda |
| DB | DynamoDB(シンプル構成、余裕があればローカルキャッシュ追加) |
| 認証 | 端末UUIDベースの軽量識別 |
| デプロイ | CloudFormation または CDK |
| 監視 | CloudWatch |
| 外部API | 天気API(OpenWeatherMap等)、HealthKit/Health Connect |
| リージョン | ap-northeast-1(Tokyo) |
| プラットフォーム | チームの実装スキルで決定(最初のBolt) |

## 非機能要件(NFR)

### 操作性
- 片手操作・最小タップで完結
- 応答速度:対話生成は数秒以内
- ダラけ感のある演出(II採用 / 新規)

### データ
- データ永続性:履歴は無限保持
- プライバシー重視:ヘルスケア生データはローカル限定、サボり履歴のみAWSに保存
- AWSサービスのみで構築(主催規約準拠)
- 日本語のみ対応

### コンセプト/トーン(新規 / 明文化)
- ユーザーを真剣に責めない
- 過剰な健康指導をしない
- 称号・対話のユーモアは品位の範囲内
- 真面目な健康相談を求めるユーザーが誤って使った場合の安全性を確保(オンボーディングでコンセプト明示)

## リスク(原則6:Risk Register / v4更新版)

| # | リスク | 重要度 | 対策方針 |
|---|---|---|---|
| R1 | フルAPI連携+二者対話+蓄積要素+発言シフト=スコープ過大 | **高** | MVPラインから絶対に下げない |
| R2 | ヘルスケアAPI連携の実装難易度・申請コスト | 高 | プラットフォーム選択時に実装力で判断、最悪は擬似データへ撤退 |
| R3 | 機微情報(ヘルスケア・位置情報)の取り扱い | 高 | ローカル保存基本、AWS送信は最小限 |
| R4 | LLM応答の品質・安全性 | 中 | プロンプト設計、両キャラがユーザーを責めないことの徹底 |
| R5 | プラットフォーム判断の遅延 | 中 | 最初のBoltで決定 |
| R6 | 「綺麗度」「迷惑リスク」の定義の曖昧さ | 中 | LLM判断型のプロンプト設計で吸収、対話のユーモアに転化 |
| R7 | 天使がうるさく感じられるリスク | 中 | 悪魔が最後の発言権、選択後は両キャラ肯定の原則を厳守 |
| R8 | AWSアカウント・権限準備の遅延 | **高** | 最初のBoltで完了させる(最優先) |
| R9 | Bedrockのモデルアクセス申請 | 中 | 最初のBoltで一緒に対応 |
| R10 | LLM呼び出し料金の予算超過 | 低 | 1日のリクエスト上限を実装、CloudWatchで監視 |
| **R11** | **倫理的リスク**:「サボりを助長する」批判への備え | **中** | 「周囲への迷惑ライン」を超えない設計、デモ説明での前置き、オンボーディングでコンセプト明示 |
| **R12** | **ユーザー層のミスマッチ**:真剣な健康相談を求める層が誤って使うリスク | **中** | オンボーディングでコンセプト・キャラクター紹介を明確に行う |
| **R13** | **称号過激化の暴走**:称号が下品/差別的になるリスク | **中** | 称号は事前リスト化し、レビュー済みのもののみ使用。LLMに動的生成させない |
| **R14** | **発言シフト仕様の複雑化**:プロンプト設計が複雑になり、応答品質が落ちる | 中 | プロンプトテストを早期に実施、Boltで段階導入 |

## ユニーク性(ハッカソン審査向け)

- **逆方向のヘルステックアプリ**:健康促進アプリの真逆を行く「ダラけさせる」コンセプト
- **ハッカソンテーマとの完全整合**:「人をダメにするサービス」を真正面から表現
- **天使と悪魔の対話**という、AIネイティブ時代ならではのインタラクション
- **本物の行動データ+天気**を根拠に天使の議論にリアリティを持たせる
- **動的な悪魔の発言シフト**:データ駆動で人格が変化するLLM活用の高度な事例
- **永続蓄積×過激な称号**で「ダメ自慢」できるリピート性
- **AWSサービスのフル活用**(Bedrock + Lambda + DynamoDB + API Gateway)で論文準拠の実装
